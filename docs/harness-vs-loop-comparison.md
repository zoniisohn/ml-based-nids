# Harness Engineering vs. Loop Engineering — Final Comparison

같은 과제(NIDS 특징 추출 → 모델 학습 → 평가 → 문서화)를 두 가지 다른 AI 협업 방식으로 독립적으로 수행한 결과를 정리한다. 세부 트러블슈팅 이력은 각 방식의 postmortem 문서([harness-postmortem.md](harness-postmortem.md), [loop-postmortem.md](loop-postmortem.md))에, 최신 수치는 [README.md](../README.md)의 "Results comparison" 표에 있다 — 이 문서는 그 둘을 종합한 최종 비교다.

## 두 방식의 정의

| | Harness Engineering | Loop Engineering |
|---|---|---|
| 구조 | 고정 파이프라인. `nids-hw-orchestrator`가 4개 전문화된 서브에이전트(특징 추출/학습/평가/리포트)를 정해진 순서로 호출 | 단일 self-referential 루프. `ralph-loop` 플러그인의 Stop hook이 세션 종료를 막고 같은 프롬프트(`RALPH_PROMPT.md`)를 매번 재주입, 역할 분담 없이 매 iteration 스스로 현재 상태를 판단 |
| 상태 관리 | 파일 기반 체크포인트(`_workspace/0N_*`)를 오케스트레이터가 관리 | 다음 iteration은 이전 iteration을 "기억"하지 못함 — `loop-engineering/` 디렉터리 내용과 `_loop_log.md`만으로 매번 처음부터 상태를 재구성 |
| 실행 단위 | 서브에이전트(전문 역할 하나씩) | 동일한 범용 에이전트가 모든 역할을 순환 수행 |

## 결과 비교

| Metric | Harness Engineering | Loop Engineering |
|--------|---------------------|-------------------|
| Time to complete | ~1.5시간 end-to-end, 그중 절반가량이 트러블슈팅(중복 프로세스, OOM 재시도, 코드 버그 2건) | 워크스페이스 스캐폴딩부터 최종 평가까지 벽시계 기준 ~1시간(특징 추출 ~17분, 모델 학습 ~45분 — OOM으로 인한 전면 재작성 1회 포함, 평가 <1분). 단, 후반부는 의도치 않게 겹친 두 번째 ralph-loop 세션과 시간이 겹쳐 있어 Harness의 단일 세션 수치와 1:1로 비교하기는 어렵다 |
| Accuracy / F1 / ROC-AUC (원 지표) | RF/XGBoost: 0.9999 / 0.9995 / 1.0000. SVM: 0.9797 / 0.9196 / 0.9889 | RF: 0.99987 / 0.99974 / 0.99999677 |
| Cross-source recall (진짜 지표) | **0.0000** (UNSW, 122,295건 중 0건 탐지) — RF/XGBoost 동일 | **0.0000** (UNSW, 122,295건 중 0건 탐지) |
| 재실행/부분 수정 용이성 | 쉬움 — 파일 기반 체크포인트 덕분에 실패한 단계만(예: 학습 단계만) 정확히 재실행 가능 | 체크포인트 시스템 없음 — 모든 iteration이 디렉터리 상태에서 "무엇이 끝났는지"를 매번 스스로 재추론. 크래시/재시작 후 자동으로 이어지지만, 특정 단계만 골라 재실행하는 기능은 없음 |
| 사람 개입 지점 | 중복 백그라운드 프로세스 종료(x2), OOM 대응 방식 결정(파라미터 조정 vs Colab vs 서브샘플링 — 사용자가 서브샘플링 선택), 서브에이전트가 만든 `UnboundLocalError` 버그 2건 진단/수정, cross-source 검증을 사람이 직접 요청 | 중복 프로세스(다른 세션과 충돌) 종료 승인 1건뿐 — OOM 완화(청크 스트리밍 재작성, 언더샘플링, 파라미터 축소)와 cross-source 검증(애초에 RALPH_PROMPT.md에 필수 항목으로 명시됨)은 전부 사람 개입 없이 루프 스스로 결정·수행 |

## 두 방식 모두가 도달한 동일한 결론

**핵심 발견은 방식과 무관하게 동일했다: 이 데이터셋은 `label`과 `source_dataset`이 100% confound되어 있어(benign=CAIDA, malicious=CIC+UNSW), random split 기반의 ~0.9999대 정확도는 "공격 탐지 능력"이 아니라 "캡처 환경 구분 능력"을 측정한다.** 두 방식 모두 cross-source held-out 검증(학습 때 전혀 보지 못한 소스로 테스트)에서 recall 0.0000을 독립적으로 재현했다. Loop Engineering 쪽은 서로의 결과를 전혀 참고할 수 없도록 격리된 워크스페이스(`loop-engineering/`, Harness의 `src/`·`.claude/agents`·`docs/harness-postmortem.md`를 읽지 않음)에서 진행됐으므로, 이 재현은 표절이 아니라 데이터셋 자체의 구조적 결함이 방식에 상관없이 드러난다는 독립적 증거다.

## 실패 모드의 성격이 다르다

같은 "8GB RAM에서 대용량 데이터를 학습한다"는 제약이 두 방식에서 다른 종류의 사고로 나타났다는 점이 이 실험에서 가장 흥미로운 부분이다.

- **Harness Engineering**의 실패는 대부분 *역할 경계와 관측 가능성*의 문제였다: 서브에이전트가 자기 프로세스의 생사만 알고 오케스트레이터가 환경에 가한 조치(중복 프로세스 종료 등)를 몰라 자기 코드 버그로 오진단했고(harness-postmortem 사건 1), 메모리 최적화 패치가 뒷단 코드와 충돌해 새 버그를 만들었다(사건 3) — 여러 역할이 파일 인터페이스로만 연결된 구조에서 나오는, "부분의 성공이 전체의 정합성을 보장하지 않는" 유형의 문제.
- **Loop Engineering**의 실패는 대부분 *동시성과 자기 진단*의 문제였다: 파라미터를 낮추는 것만으로는 부족해 데이터 로드 방식 자체(스트리밍)를 바꿔야 했고(loop-postmortem 사건 1), 무엇보다 상태 없는 루프가 파일시스템만으로 조율되다 보니 **다른 세션과의 존재조차 몰랐던 충돌**이 발생했다(사건 2) — 이는 Harness Engineering 쪽 구조에서는 애초에 발생할 수 없는 실패 모드다(오케스트레이터 하나가 모든 서브에이전트 실행을 직렬화하기 때문).

두 경우 모두 결국 **파일/프로세스 상태를 스냅샷 한 번이 아니라 직접, 반복적으로 재확인하는 습관**이 실패를 잡아낸 핵심 수단이었다는 점은 공통적이다.

## 요약

| | Harness Engineering | Loop Engineering |
|---|---|---|
| 강점 | 명확한 역할 분담으로 실패 지점을 정확히 특정·재실행 가능. 사람이 각 단계 산출물을 검토할 자연스러운 체크포인트가 있음 | 사람 개입 없이 자기 진단·자기 수정하는 범위가 훨씬 넓음(OOM 대응, 필수 검증 수행 모두 자동). 워크스페이스 격리로 독립 재현 실험에 적합 |
| 약점 | 역할 경계 밖 실패(리소스 고갈, 타이밍 레이스)를 누가 감시할지 설계에서 빠지기 쉬움. 오케스트레이터가 결국 환경 감시자 역할까지 떠안음 | 동시성 격리가 구조적으로 없음 — 상태 파일 하나를 여러 세션이 공유하면 충돌. 장시간 대기가 필요한 작업에서 iteration 예산이 "대기 확인"에 소모되기 쉬움 |
| 이번 실행에서 사람이 반드시 필요했던 지점 | 4곳(중복 프로세스, OOM 전략 선택, 코드 버그 2건, cross-source 검증 요청) | 1곳(세션 간 중복 프로세스 종료 승인) — 단, cross-source 검증 자체는 애초에 프롬프트에 필수 항목으로 못박혀 있었기에 "사람이 그때그때 요청"할 필요가 없었다는 점은 감안해야 한다 |
