# Loop Engineering Postmortem

이 문서는 `ralph-loop` 플러그인으로 `loop-engineering/RALPH_PROMPT.md`를 반복 재주입하는 방식(Loop Engineering)으로 NIDS 과제를 실제로 돌리면서 겪은 문제들, 진단 과정, 해결 방법, 그리고 거기서 얻은 일반 원칙을 기록한다. 고정된 서브에이전트 역할 분담 없이 "매 iteration마다 파일/로그만 보고 스스로 판단"하는 방식이 실제로 어떤 종류의 고장을 내는지, 그리고 그 방식이 Harness Engineering과 근본적으로 다른 지점이 어디인지를 남기는 것이 목적이다. 짝을 이루는 문서는 [docs/harness-postmortem.md](harness-postmortem.md), 전체 원본 로그는 [loop-engineering/_loop_log.md](../loop-engineering/_loop_log.md)(git 미추적, 로컬 전용).

## TL;DR

- 13번의 iteration 중 절반 이상(iter 3~9)이 같은 문제 하나 — 8GB RAM 머신에서 220만 행 RandomForest 학습이 시스템 전체 메모리 압박으로 두 번 조용히 죽은 것 — 를 진단하고 고치는 데 들어갔다. 프로세스 자체 메모리는 항상 작았고(~300MB), 문제는 다른 앱까지 포함한 시스템 전체 여유 메모리였다.
- 파라미터를 낮추는 것(1차 대응)만으로는 부족했다 — 근본 원인은 `pd.read_csv`가 **필터링 이전에 220만 행 전체를 메모리에 올리는 것** 자체였고, 청크 스트리밍 + 다수 클래스 언더샘플링으로 로드 단계 자체의 peak 메모리를 낮추고 나서야 완주했다.
- **가장 특징적인 사건**: 이 루프와 별개로 **다른 Claude Code 세션이 같은 프로젝트에서 같은 ralph-loop 작업을 동시에 진행**하고 있었다 — 서로의 존재를 몰랐던 두 세션이 같은 `_loop_log.md`/`train_model.py` 산출물 경로를 공유하다 프로세스가 중복 실행됐다. Harness Engineering에서는 있을 수 없는, "메모리를 공유하지 않는 상태 없는(stateless) 루프가 파일시스템만으로 조율된다"는 구조 자체에서 나온 실패 모드다.
- 그럼에도 불구하고 두 세션은 각자 독립적으로 같은 결론(cross-source recall = 0.0000, Harness가 발견한 것과 동일한 label/source_dataset confound)에 도달했고, 거의 동시에 완료 신호를 냈다 — 최종 산출물은 충돌 없이 하나로 수렴했다.

## 사건 기록

### 사건 1 — 8GB RAM 머신에서 220만 행 RandomForest 학습이 두 번 조용히 죽음

**증상**: iter 2에서 `train_model.py`(전체 2,226,498행, `n_jobs=2`, `n_estimators=200`, `max_depth=20`)를 백그라운드로 시작한 뒤, iter 3~7 내내(약 25분 이상) `loop-engineering/models/`가 계속 비어 있었다. 매 iteration 프로세스 생존과 CPU 사용 시간 증가를 확인해 "멈춘 게 아니라 진행 중"으로 판단하고 대기했으나, iter 8에서 결국 프로세스가 사라지고 첫 번째 모델(standard)조차 저장하지 못한 채 종료된 것을 확인했다. Python 예외도 traceback도 없었다.

**진단**: 시스템 메모리(`Get-CimInstance Win32_OperatingSystem`)를 확인하니 총 7.72GB 중 여유가 0.33~0.41GB 수준이었다. `train_model.py` 프로세스 자체의 WorkingSet은 계속 ~300MB로 작았으므로 압박의 주 원인은 다른 앱(Code/Chrome 등)이었지만, 그 좁은 여유 안에서 RandomForest 학습이 OS에 의해 강제 종료된 것으로 판단했다.

**1차 해결(부족)**: RALPH_PROMPT.md의 지시("같은 지점에서 반복 실패하면 병렬도를 낮추거나 subsample")에 따라 `n_jobs=2→1`, `n_estimators=200→100`, `max_depth=20→15`로 낮추고, 다수 클래스(caida)를 소수 클래스 대비 3배로 언더샘플링해 재실행했다(iter 8). **그런데도 iter 9에서 정확히 같은 방식으로, 이번엔 첫 로그 줄(`streamed rows`)조차 찍히기 전에 다시 죽었다.** 원인 재분석: 언더샘플링은 `pd.read_csv`로 **전체를 다 읽어들인 뒤** 적용되고 있었다 — 로드 시점 자체에는 여전히 220만 행 전체(19개 컬럼, dtype 미지정)가 메모리에 올라갔다.

**최종 해결**: `train_model.py`를 청크 스트리밍 방식으로 재작성했다 — `pd.read_csv(..., usecols=필요한 컬럼만, dtype=float32/int32/int16/int8, chunksize=200_000)`으로 청크 단위로 읽으면서, 다수 클래스(caida)만 청크마다 확률적으로 언더샘플링(`rng.random() < prob`)해 caida 전체를 한 번도 완전한 형태로 메모리에 올리지 않도록 했다. peak 메모리가 파일 전체 크기가 아니라 청크 크기(20만 행) 수준으로 제한되면서, 이후 재실행(iter 10~13, WorkingSet ~110~440MB)은 끝까지 완주했다(standard 533초, cross_source 153초).

### 사건 2 — 다른 Claude Code 세션과의 동시 실행 충돌

**증상**: iter 10에서 프로세스 목록을 확인하다가 동일한 `train_model.py`를 실행하는 python.exe가 **동시에 2개**(각각 17:30:00, 17:30:15 시작) 떠 있는 것을 발견했다. 더 결정적인 단서: `_loop_log.md`에 이 세션이 작성한 적 없는 `iter 8`, `iter 9` 항목이 이미 존재했다 — 파일 내용을 기준으로만 상태를 판단하는 루프 설계 특성상, 처음에는 이게 "내가 기억 못 하는 내 과거 iteration"인지 "다른 주체가 쓴 것"인지 구분이 안 됐다.

**진단**: 이 프로젝트의 ralph-loop 상태 파일(`.claude/ralph-loop.local.md`)은 세션 하나에만 바인딩되는데, 이 세션을 시작하기 직전에 "이미 진행 중이던 다른 세션(`session_id: fe875a7a-...`)의 loop를 이 세션(`247e0b1c-...`)으로 재바인딩"하는 작업이 있었다. 재바인딩은 상태 파일의 `session_id`만 덮어쓸 뿐, 그 순간 다른 세션이 이미 진행 중이던 턴을 강제 종료시키지는 못한다 — 그 세션은 자신의 Stop hook이 다음에 발동해 세션 불일치를 확인하기 전까지 몇 차례 iteration을 그대로 더 진행했고, 그 결과가 iter 8/9/12/13으로 `_loop_log.md`에 계속 쓰였다. 두 세션이 "학습 프로세스가 안 보인다"는 같은 관찰을 거의 동시에 하고 각자 재시작을 시도하면서 프로세스가 중복됐다.

**해결**: 같은 출력 파일(`models/*.joblib`, `_train_log.txt`)에 두 프로세스가 동시에 쓰면 손상/경쟁 및 메모리 이중 소모 위험이 있어 즉시 하나를 종료하려 했으나, `Stop-Process`가 Claude Code의 자동 승인 분류기에 의해 차단됐다(파괴적 작업). 사용자에게 상황을 설명하고 `AskUserQuestion`으로 승인을 받은 뒤 나중에 시작된 프로세스(PID 6664)만 종료하고 먼저 시작된 것(PID 8468)을 남겼다. 이 세션이 자체적으로 재시작을 시도한 백그라운드 실행은 `exit code 127`(백그라운드 셸 컨텍스트에서 `python` PATH 미인식)로 즉시 실패했는데, 결과적으로 무해했다 — 어차피 살아있는 프로세스가 있었기 때문이다. 이후 두 세션은 충돌 없이 각자 관찰을 계속했고, 최종적으로 동일한 산출물(같은 `eval_results.json` 수치)을 놓고 **거의 동시에 독립적으로** `<promise>LOOP_NIDS_DONE</promise>`을 출력했다 — 어느 쪽도 상대의 최신 판단을 몰랐지만 결과는 충돌 없이 수렴했다.

## 일반 원칙 (트러블슈팅 체크리스트)

1. **"메모리가 부족하다"와 "이 스크립트가 메모리를 많이 쓴다"는 다른 문제다.** 학습 프로세스 자체 WorkingSet은 항상 300MB 이하였는데도 시스템 전체 여유가 0.3~0.4GB뿐이라 죽었다 — 원인 진단은 항상 프로세스 단위가 아니라 시스템 전체(`Get-CimInstance Win32_OperatingSystem`) 단위로 먼저 확인해야 한다. (사건 1)
2. **파라미터를 낮췄는데도 같은 지점에서 또 죽으면, 문제는 파라미터가 아니라 데이터 로드 방식 자체를 의심하라.** `n_jobs`/`n_estimators`를 낮춘 재시도가 실패하자 비로소 `pd.read_csv`가 필터링 전에 전체를 메모리에 올린다는 진짜 원인을 찾았다 — 스트리밍/청크 처리로 바꾸고서야 해결됐다. (사건 1)
3. **CPU 사용 시간의 증가 여부로 "멈췄다"와 "느리지만 진행 중이다"를 구분하라.** 프로세스 생존만 보고 판단하면 안 된다 — 매번 짧은 간격을 두고 CPU 시간을 두 번 읽어 델타가 양수인지 확인하는 습관이, 정상 진행 중인 25분짜리 학습을 성급하게 죽이는 것을 막아줬다. (사건 1)
4. **파일/디렉터리 상태만으로 진행 상황을 파악하는 루프는, 그 파일을 다른 주체가 건드릴 수 있다는 가능성을 항상 열어둬야 한다.** `_loop_log.md`에 내가 쓴 적 없는 항목이 있다는 것 자체가 "다른 프로세스가 같은 상태 공간에서 동작 중"이라는 가장 확실한 신호였다 — 매 iteration 로그를 append하기 *전에* 마지막 항목이 자신이 방금 쓴 것인지 먼저 확인하는 습관이 이 신호를 빨리 잡아냈다. (사건 2)
5. **의심스러운 중복/충돌을 발견해도, 그걸 없애는 행위(프로세스 kill 등)는 되돌리기 어려운 조치이므로 자동 승인 범위 밖일 수 있다.** 이럴 때는 스스로 판단해 조용히 처리하려 하지 말고, 상황을 설명하고 승인을 구하는 편이 안전하다 — 특히 어느 프로세스가 "진짜"이고 어느 게 "중복"인지조차 100% 확신할 수 없는 상황에서는 더욱 그렇다. (사건 2)
6. **완료 판단은 감사 추적(로그)에 근거해야지, "내가 다 했다"는 자기 확신에 근거하면 안 된다.** 두 세션이 완료를 선언하기 전 각각 파일 시스템을 직접 재점검(`models/*.joblib`, `results.md`의 TBD 잔존 여부, README 수치 일치 여부)했기 때문에, 서로의 작업을 몰랐음에도 결과가 어긋나지 않았다. (사건 2)

## Loop Engineering의 특징적 문제

이번 실행에서 반복적으로 드러난, "고정 역할 분담 없이 파일 상태만으로 스스로 판단하는 루프" 구조 자체에 내재한 문제들:

- **동시성 격리가 설계에 없다.** Harness Engineering은 오케스트레이터 하나가 서브에이전트를 순차/병렬로 명시적으로 조율하지만, ralph-loop은 "세션 하나가 상태 파일 하나를 갱신하며 반복"하는 것을 전제로 한다. 같은 프로젝트에 대해 세션이 두 개 이상 활성화될 수 있다는 것 자체는 막지 않기 때문에, 상태 파일 재바인딩처럼 사소해 보이는 조작이 두 루프의 충돌로 이어질 수 있다. (사건 2)
- **"이전 iteration의 기억이 없다"는 설계가 장점이자 취약점이다.** 매 iteration이 파일만 보고 스스로 판단하게 한 덕분에 세션이 바뀌어도(그리고 두 세션이 겹쳐도) 각자 일관되게 다음 행동을 판단할 수 있었다(사건 1의 대기/재시도 판단이 iteration마다 끊김 없이 이어졌다) — 그러나 바로 그 이유로 "지금 이 파일 상태를 만든 게 나인지 남인지"를 구분할 방법이 파일 내용 자체 말고는 없다. (사건 2)
- **대기가 필요한 장시간 작업에서 iteration이 세분화되며 낭비가 생기기 쉽다.** Stop hook이 매 iteration마다 새 턴을 여는 구조라, 학습이 몇 분~수십 분 걸리는 동안 "아직 안 끝났다"만 반복 확인하는 iteration이 여러 번 소모됐다(iter 3~7, 11). 한 턴 안에서 폴링 루프(`sleep` 반복)로 여러 분을 흡수하는 방식으로 완화했지만, 근본적으로 iteration 예산(여기서는 최대 40회)을 "실질적 작업"과 "그냥 기다림"이 나눠 쓰는 구조다.
- **완료 판단 기준(`<promise>`)이 텍스트 매칭이라 정확해야 한다.** 이 실험은 문제 없이 지나갔지만, 두 세션이 동시에 완료 조건을 만족했을 때 그중 하나라도 promise 문구를 잘못 쓰거나 조건을 성급히 판단했다면 조용히 미완성 상태로 종료될 수 있었다 — Harness의 오케스트레이터처럼 "완료"를 다시 검증하는 별도 주체가 없다.

## 다음에 다르게 할 것

- 대용량 CSV를 다루는 학습 스크립트는 처음부터 청크 스트리밍으로 작성한다 — "일단 전체를 불러온 뒤 걸러낸다"는 접근은 8GB RAM 환경에서는 데이터 크기와 무관하게 항상 의심해야 한다 (지금은 OOM을 두 번 겪고 나서야 역산했다).
- ralph-loop을 다른 세션으로 재바인딩하기 전에, 재바인딩 대상 상태 파일이 가리키는 세션이 실제로 종료됐는지(혹은 최소한 지금 활성 턴이 없는지)를 먼저 확인하는 습관을 들인다 — 지금은 재바인딩 시점에 이미 이 위험을 인지하고 사용자에게 물었지만, 실제 충돌은 그 이후에도 발생했다.
- 매 iteration 시작 시 `_loop_log.md`의 마지막 항목 작성자(자신인지 아닌지)를 명시적으로 확인하는 절차를 RALPH_PROMPT.md 자체에 넣으면, 동시 실행 감지가 사건 2처럼 우연히 프로세스 목록을 보다가 발견되는 대신 더 빨리, 더 확실하게 이뤄질 것이다.
- 장시간 백그라운드 작업을 기다리는 iteration에서는 매번 새 턴을 여는 대신, 한 턴 안에서 폴링(sleep 반복)으로 최대한 흡수해 iteration 예산을 아낀다 — 이번 실행에서 후반부에 적용해 효과를 봤다(5분씩 두 번의 폴링으로 iter 12→13 사이 여러 번의 "아직 안 끝남" iteration을 건너뛸 수 있었다).
