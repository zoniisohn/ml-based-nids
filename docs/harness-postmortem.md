# Harness Engineering Postmortem

이 문서는 `nids-hw-orchestrator` 하네스로 NIDS 과제 파이프라인(특징 추출 → 모델 학습 → 평가 → 문서화)을 실제로 돌리면서 겪은 문제들, 진단 과정, 해결 방법, 그리고 거기서 얻은 일반 원칙을 기록한다. Harness Engineering 방식이 실제로 어떤 종류의 고장을 내는지, 그리고 오케스트레이터가 어떤 역할을 해야 그걸 잡아낼 수 있는지를 남기는 것이 목적이다.

## TL;DR

- 서브에이전트의 "완료했다"는 자기 보고와 실제 산출물 존재 여부는 별개다 — 총 3개 사건(중복 프로세스, 조용한 OOM, 자체 모니터링 오탐)이 전부 이 간극에서 나왔다.
- 파라미터 튜닝으로 못 고치는 문제(메모리 부족)를 파라미터로 계속 고치려 하면 시간만 소모한다 — 근본 원인(가용 메모리 자체)을 먼저 확인해야 한다.
- 메모리 최적화용 패치(`del` + `gc.collect()`)가 그 자체로 새로운 버그 클래스를 만들었다 — 최적화 코드는 일반 로직 코드보다 더 의심해야 한다.
- **가장 중요한 발견**: 파이프라인 각 단계가 다 "정상 작동"해도 결과가 틀릴 수 있다. 평가 단계가 계산한 99.99%라는 지표 자체는 정확했지만(재계산으로 검증됨), 그 지표가 측정하는 대상 자체가 잘못 설계되어 있었다(데이터 소스와 라벨의 완전한 confounding). 이건 어느 서브에이전트의 코드 버그도 아니고, 파이프라인을 아무리 잘 실행해도 저절로 드러나지 않는다.

## 사건 기록

### 사건 1 — 특징 추출 단계에서 중복 백그라운드 프로세스

**증상**: `flow-feature-engineer` 서브에이전트가 "여전히 실행 중"이라고 반복 보고. 오케스트레이터가 직접 `ps aux`/`Get-CimInstance Win32_Process`로 확인하니 동일한 `src/feature_extraction.py`를 실행하는 python 프로세스가 **2개, 그리고 나중에 한 번 더** 동시에 떠 있었다.

**진단**: 서브에이전트는 정상적으로 백그라운드 작업(`run_in_background`)을 걸었지만, 그 결과를 나중에 조회했을 때 `exited with code 127`을 받았다. 이는 실제로는 오케스트레이터가 (뒤늦게 발견한) 중복 프로세스를 죽인 부작용이었는데, 서브에이전트는 이를 "내 백그라운드 실행 자체가 잘못됐다(PATH 문제 등)"로 오인했다. PATH를 의심해 절대경로로 재실행 → 또 같은 duplicate-kill에 걸려 또 127 → 이 패턴이 반복되면서 동일 스크립트가 여러 번 중복 실행됐다.

**해결**: 오케스트레이터가 OS 프로세스 목록을 직접 조회해 중복을 찾아내고, 가장 먼저 시작된(진행이 가장 많이 된) 프로세스만 남기고 나머지를 종료. 서브에이전트에게 "더 이상 재실행하지 말고 기존 프로세스 완료를 기다리라"고 명시적으로 메시지를 보내 개입을 멈췄다. 서브에이전트도 결국 스스로 `echo hello`, `python --version` 같은 최소 단위 대조 실험으로 "이게 진짜 PATH 문제인지, 아니면 실행 환경이 내 중복 실행을 막고 있는 것인지"를 격리해서 스스로 올바른 결론에 도달했다.

### 사건 2 — 모델 학습 단계에서 조용한 OOM

**증상**: `ids-model-trainer`가 `RandomForestClassifier` 학습을 시작한 직후 로그가 완전히 끊기고 프로세스가 사라짐. Python 예외도, traceback도 없었다.

**진단**: 시스템 메모리를 직접 확인(`Get-CimInstance Win32_OperatingSystem`) — 총 7.7GB 중 여유 메모리가 학습 시작 전부터 이미 0.4~0.9GB 수준. `n_jobs=-1`로 설정된 RF/XGBoost가 Windows의 joblib(loky) 병렬 백엔드에서 워커마다 데이터를 복제하면서 메모리를 다 써버리고 OS에 의해 강제 종료(OOM kill)된 것으로 결론. 예외가 아니라 강제 종료라 Python의 `try/except`로도 못 잡는다.

**1차 해결 시도(부족)**: `n_jobs`를 1~2로 제한, `n_estimators`/`max_depth` 축소, 특징을 float32로 다운캐스트, 단계마다 `del` + `gc.collect()`로 즉시 메모리 회수, 전체를 `try/except`로 감싸 실패 시 traceback을 남기도록 방어 코드 추가. **그런데도 정확히 같은 지점에서 다시 조용히 죽었다** — 이는 이 문제가 스크립트 파라미터 수준이 아니라, 애초에 시스템 전체에 남은 여유 메모리 자체가 부족하다는 것을 보여준다(사용자도 실제로 컴퓨터가 버벅여 Esc로 중단시켰다고 확인).

**의사결정**: 이 시점에서 "로컬에서 계속 파라미터를 조정할지 vs. Google Colab 같은 외부 환경으로 옮길지"를 판단해야 했다. Colab은 메모리 자체는 넉넉하지만, 이 프로젝트는 하네스가 로컬 git 저장소를 직접 읽고 쓰는 구조라 Colab으로 가면 업로드/다운로드라는 수동 단계가 끼어들어 자동화 흐름이 끊긴다. 대신 학습에 쓰는 데이터 자체를 stratified subsampling(178만 행 → 40만 행)해서 메모리 요구량을 근본적으로 낮추는 쪽을 택했다 — 과제 수준 분류기 검증에는 충분한 규모이면서 하네스 자동화는 그대로 유지된다.

**최종 해결**: 40만 행 서브샘플링 적용 후 학습이 2분 내에 완주했다(이전엔 언제 끝날지 알 수 없는 채로 반복 실패).

### 사건 3 — 메모리 최적화 패치가 만든 두 개의 `UnboundLocalError`

**증상**: OOM은 해결됐는데, 이번엔 세 모델(RF/XGBoost/SVM) 학습과 예측 저장까지 전부 성공한 뒤, 스크립트 맨 끝(메타데이터 JSON 저장 직전)에서 `UnboundLocalError: cannot access local variable 'df' where it is not associated with a value`로 죽었다. 재실행하니 이번엔 같은 유형의 에러가 다른 변수(`X_svm_train`)에서 또 발생했다.

**진단**: 사건 2에서 메모리를 아끼려고 넣은 `del df`, `del svm_clf, X_svm_train, y_svm_train` 같은 코드가, 스크립트 뒷부분에서 메타데이터를 만들 때 그 변수들을 다시 참조하는 기존 코드와 충돌했다. Python은 함수 안에서 한 번이라도 대입된 변수는 그 함수 전체에서 "로컬 변수"로 취급하기 때문에, `del` 이후에 참조하면 `NameError`가 아니라 `UnboundLocalError`가 난다.

**해결**: `del`하기 직전에 필요한 값(예: `len(df)`)을 별도의 스칼라 변수(`n_subsampled`)에 미리 저장해두고, 이후 코드는 원본 변수 대신 그 스칼라를 참조하도록 수정. 첫 번째 버그를 고친 뒤 재실행에서 두 번째(동일 유형) 버그가 또 나오자, 세 번째로 또 당하지 않기 위해 스크립트 전체에서 `del`/`gc.collect()`가 등장하는 모든 위치를 `grep`으로 찾아 그 이후 코드가 삭제된 변수를 참조하지 않는지 한 번에 전수 점검했다 — 이후로는 이 유형의 버그가 재발하지 않았다.

### 사건 4 — 오케스트레이터 자신의 모니터링 스크립트가 낸 오탐 (3회)

**증상**: 오케스트레이터가 학습 완료를 감지하려고 걸어둔 백그라운드 폴링 스크립트(`Monitor`)가 "python 프로세스가 없고 산출물도 없다 → 멈췄거나 죽었다"는 신호를 최소 세 번 보냈는데, 실제로는 (a) 프로세스가 막 시작되는 타이밍에 걸려서, 또는 (b) 학습 스크립트 자체는 이미 성공적으로 끝났지만 서브에이전트가 요약 파일(`02_trainer_summary.md`)을 쓰기 전의 짧은 틈에 걸려서 발생한 오탐이었다.

**진단**: 한 시점의 스냅샷만으로 "프로세스 생존 여부 + 산출물 존재 여부"를 판단하면, 프로세스 생명주기의 시작/끝 경계에서 레이스 컨디션이 생긴다.

**해결**: "프로세스 없음"이 3번 연속 확인될 때만 최종 판단하도록 디바운싱을 추가했고, 무엇보다 모니터가 "죽었다"는 신호를 보내도 그걸 사실로 받아들이지 않고 매번 로그/프로세스/산출물 파일을 직접 다시 확인하는 습관으로 대응했다. 이 덕분에 실제로 정상 종료였던 두 번의 오탐을 "재실행 필요"로 잘못 처리하지 않을 수 있었다.

### 사건 5 — 교차 소스 검증으로 드러난 데이터 누수 (가장 중요한 발견)

**증상**: 평가 결과가 RF/XGBoost 기준 Accuracy/F1 ≈ 0.9999, ROC-AUC ≈ 1.0000으로 지나치게 높게 나왔다.

**직관적 경보**: 보안 분류 문제에서 거의 완벽한 성능은 "모델이 훌륭하다"보다 "데이터 설계에 문제가 있다"는 신호로 먼저 의심해야 한다. 평가를 맡은 서브에이전트 스스로도 요청받지 않았음에도 이 문제를 지적했다: 라벨링 방식상 benign=CAIDA, malicious=CIC+UNSW로 **라벨과 데이터 소스가 100% 겹친다** — "공격인지 판별"과 "어느 캡처 장비에서 왔는지 판별"이 데이터 구조상 완전히 동일한 문제가 되어 있었다.

**검증 (2단계)**:
1. **독립 재계산**: 평가 서브에이전트가 보고한 수치를 신뢰하지 않고, `_workspace/02_trainer_test_predictions.csv`의 원본 예측값에서 Accuracy/Precision/Recall/F1/ROC-AUC를 직접 다시 계산 — 소수점까지 완전히 일치함을 확인. 즉 "계산 실수"는 배제됨.
2. **Cross-source(교차 소스) 검증**: CAIDA(benign)+CIC(malicious)로만 학습하고, 학습 때 전혀 보지 않은 malicious 소스인 UNSW 전체(122,295건)를 테스트에 포함시켜 재현율을 측정.

**결과**: RF/XGBoost 모두 UNSW에 대한 재현율이 **정확히 0.0000** — 122,295건의 공격을 단 한 건도 탐지하지 못했다. 반면 held-out CAIDA(benign)에 대해서는 여전히 99.98~99.99% 정확했다.

**결론**: 모델은 "공격 트래픽의 행동 패턴"을 학습한 것이 아니라 "CIC 캡처 환경 특유의 아티팩트"를 학습해서 malicious=CIC라는 등식을 외운 것이다. UNSW는 다른 환경이라 그 아티팩트가 없으므로 malicious로 전혀 인식되지 않는다. 라벨이 nuisance 변수(캡처 소스)와 완전히 confound된 상태에서 나온 지표는, 그 지표 자체가 아무리 정확하게 계산됐어도 원래 측정하려던 것(침입 탐지 능력)을 측정하지 못한다.

### 사건 6 — 완화 시도: leak feature 제거로 cross-source recall 개선 시도 (실패, 구조적 한계로 확인)

**증상/동기**: 사건 5에서 데이터 누수(라벨-소스 confounding)가 확인된 뒤, "그럼 문제가 되는 feature만 골라 제거하면 고쳐지는가"를 확인해볼 필요가 있었다 — 국소적인 feature 선택 문제인지, 데이터셋 자체의 구조적 문제인지가 아직 구분되지 않은 상태였다.

**진단**: malicious 서브셋(CIC vs UNSW)만 떼어서 봤다 — 이 둘은 라벨이 둘 다 1(malicious)로 동일하므로, 이 서브셋 안에서 "소스가 CIC인지 UNSW인지"를 예측하는 신호는 정의상 라벨 정보와 무관하게 순수한 환경 아티팩트다. 이 소스 식별 분류기를 학습했더니 **정확도 100%** — 두 malicious 소스가 feature 공간에서 완전히 분리되어 있었다. 기여도 상위 5개 feature(`protocol` 0.49, `byte_count` 0.14, `pkt_size_max` 0.12, `packet_count` 0.07, `pkt_size_mean` 0.06)가 threshold(0.05) 이상으로 flag됐다.

**해결 시도**: 이 5개 feature를 제거하고 남은 9개(`flow_duration`, `pkt_size_min/std`, `iat_mean/min/max/std`, `pkt_size_entropy`, `iat_entropy`)만으로 사건 5와 동일한 cross-source 분할(CAIDA+CIC 학습 → UNSW 테스트)을 다시 실행했다.

**결과**: UNSW recall은 **0.0000 → 0.0000, 변화 없음**. ROC-AUC만 ~1.0에서 0.78~0.81로 소폭 하락(모델이 예전만큼 확신하진 못하지만 0.5 threshold에서의 판정은 그대로 전부 틀림). 즉 "가장 의심스러운 5개"를 빼도 남은 9개 feature만으로 여전히 두 환경을 구분해버릴 만큼 신호가 광범위하게 퍼져 있었다.

**결론과 의미**: 데이터 누수가 "몇 개 feature의 문제"가 아니라 이 데이터셋의 flow-level 통계 자체가 캡처 도구/환경마다 근본적으로 다른 분포를 갖는 **구조적 문제**라는 게 확인됐다. Feature 엔지니어링으로는 해결할 수 없고, 진짜 해결에는 라벨과 소스가 confound되지 않은 새로운 데이터(예: CAIDA 환경에서 캡처한 malicious 트래픽, 또는 CIC/UNSW 환경에서 캡처한 benign 트래픽)가 필요하다. 그럼에도 이 실패한 시도는 무의미하지 않았다 — 오히려 "국소적 수정으로 안 고쳐진다"는 결과 자체가 문제의 범위(국소적 vs 구조적)를 명확히 규명해준 diagnostic 실험이었다. 만약 recall이 개선됐다면 반대로 "일부 feature만 문제였다"는 다른 결론에 도달했을 것이다. 또한 "라벨이 상수인 서브그룹 안에서 nuisance 변수(소스)를 예측하는 보조 분류기를 학습해 feature importance를 본다"는 기법 자체는, 향후 다른 데이터셋에서도 재사용 가능한 누수-범위 진단 방법으로 남길 만하다.

## 일반 원칙 (트러블슈팅 체크리스트)

1. **서브에이전트의 "완료" 보고를 곧이곧대로 믿지 마라.** 비동기 서브에이전트는 자기 턴이 끝나는 시점과 실제 작업이 끝나는 시점이 다르다. 다음 단계로 넘어가기 전에 산출물 파일이 실제로 존재하고 내용이 그럴듯한지 오케스트레이터가 직접 확인해야 한다. (사건 1, 4)
2. **에러 메시지 없이 백그라운드 작업이 조용히 사라지면 OOM을 먼저 의심하라.** Python 예외가 아니라 OS가 강제 종료한 것이라 애플리케이션 로그에 흔적이 안 남는다. 코드를 고치기 전에 시스템 메모리부터 확인하라. (사건 2)
3. **파라미터 튜닝으로 안 되는 문제를 파라미터로 계속 두드리지 마라.** 같은 지점에서 같은 방식으로 반복 실패한다면, 문제의 스케일이 파라미터 조정 수준을 넘어선 것이다 — 데이터/작업 규모 자체를 줄이거나 환경을 바꾸는 결정을 내려야 한다. (사건 2)
4. **최적화 패치는 일반 로직보다 더 의심하라.** 메모리 절약을 위해 넣은 `del`/조기 해제 코드가, 그 변수를 나중에 다시 쓰는 기존 코드와 충돌해 새로운 버그를 만들 수 있다. 이런 패치를 넣을 땐 그 변수의 모든 이후 참조를 한 번에 점검하라 (하나 고치고 재실행 → 또 걸리는 식으로 낭비하지 말 것). (사건 3)
5. **감시 도구 자신도 틀릴 수 있다.** 프로세스 생존을 스냅샷 한 번으로 판단하는 폴링은 시작/종료 경계에서 오탐을 낸다. 디바운싱하고, "실패했다"는 신호 자체를 직접 재검증 없이 행동의 근거로 삼지 마라. (사건 4)
6. **지나치게 좋은 지표는 성공이 아니라 경보로 취급하라.** 특히 보안/이상탐지처럼 클래스가 불균형하고 라벨링에 휴리스틱이 섞이기 쉬운 문제에서, 거의 완벽한 성능은 데이터 누수(라벨과 nuisance 변수의 confounding)를 의심할 첫 번째 신호다. 검증은 계산이 맞았는지(재계산)와,애초에 측정 설계가 맞았는지(분포를 바꾼 홀드아웃, 여기서는 cross-source) 두 층위로 나눠서 해야 한다. (사건 5)
7. **완화 시도의 실패도 진단 정보다.** "이 수정으로 고쳐지지 않았다"에서 멈추지 말고, 왜 안 고쳐졌는지에서 문제의 범위(국소적 feature 문제 vs 데이터셋 구조 문제)에 대한 결론을 끌어내라. 라벨이 상수인 서브그룹 안에서 nuisance 변수를 예측하는 보조 분류기로 feature importance를 보는 것은, 누수가 몇 개 feature에 국한되는지 아니면 전반적인지를 구분하는 재사용 가능한 진단 기법이다. (사건 6)

## 하네스 엔지니어링의 특징적 문제

이번 실행에서 반복적으로 드러난, 파이프라인형 하네스 구조 자체에 내재한 문제들:

- **관측 가능성의 비대칭.** 각 서브에이전트는 자기 프로세스의 생사만 알고, 오케스트레이터나 다른 서브에이전트가 환경에 가한 조치(예: 중복 프로세스 종료)는 알 수 없다. 그 결과 외부 요인으로 생긴 실패를 자기 코드 문제로 오진단하고 잘못된 방향으로 디버깅하게 된다(사건 1). 하네스가 커질수록 "누가 무엇을 방금 건드렸는지"를 각 에이전트에게 알려주는 장치가 없으면 이런 오진단이 반복된다.
- **책임 경계 밖의 실패 모드.** 리소스 고갈(OOM), 타이밍 레이스 같은 문제는 특정 서브에이전트의 코드 품질과 무관하게 "환경"에서 발생한다. 파이프라인을 역할별로 쪼갤 때 이런 환경 차원의 문제를 누가 감시할지가 설계에서 빠지기 쉽다 — 결국 오케스트레이터가 프로세스 목록·메모리 상태 같은 환경 신호를 직접, 지속적으로 확인하는 역할을 떠안아야 했다.
- **국소적 성공의 합이 전체적 정합성을 보장하지 않는다.** 특징 추출, 학습, 평가 세 단계가 각각 "자기 할 일"을 정확히 해냈음에도(평가 수치는 재계산으로 검증됨) 파이프라인 전체의 결론(이 모델은 침입을 탐지한다)은 틀렸다. 각 단계가 인터페이스(파일)만 맞춰 산출물을 넘기는 구조에서는, 앞 단계의 설계 결정(라벨링 방식)이 가진 근본적 결함을 뒤 단계 중 누구도 자기 책임 범위 안에서 검증하지 않는다 — 실제로는 평가 서브에이전트가 자발적으로 이상 징후를 지적했기에 드러났을 뿐, 파이프라인 구조 자체가 이를 강제하지는 않았다.
- **재시도 비용이 비대칭적으로 싸거나 비싸다.** 파일 기반 체크포인트(`_workspace/0N_*`) 덕분에 실패한 단계만 다시 돌리는 건 쌌지만(예: 학습 단계만 4번 재시도), 그 재시도 하나하나가 실제로는 몇 분(대용량 데이터 처리)에서 거의 즉시(버그 수정 후 재실행)까지 편차가 컸다. 재시도가 "저렴해 보인다"는 이유로 근본 원인 분석 없이 반복 재시도부터 시도하면(사건 2의 1차 시도들처럼) 오히려 시간을 더 쓰게 된다.
- **정형 파이프라인은 "이 문제가 이 데이터로 풀릴 수 있는가" 자체를 검증하지 않는다.** 4단계(추출-학습-평가-보고)는 각자 맡은 산출물을 만드는 데는 충실하지만, 그 산출물들이 전제하는 문제 설정 자체가 실현 가능한지는 누구의 책임 범위에도 들어있지 않다. 데이터 누수의 존재(사건 5)와 그것이 feature 수정으로 해결 불가능한 구조적 한계라는 사실(사건 6)은 둘 다 파이프라인 바깥에서 사람이 요청한 별도 분석으로만 드러났다 — 표준 4단계만 반복 실행했다면 영원히 몰랐을 것이다.

## 다음에 다르게 할 것

- 학습 스크립트를 작성할 때 처음부터 데이터 규모/메모리 예산을 먼저 계산하고 `n_jobs`, 서브샘플링 여부를 결정한 뒤 작성한다 (지금은 OOM을 실제로 겪고 나서야 역산했다).
- 메모리 최적화용 `del`을 넣을 때는 그 스코프에서 해당 변수의 마지막 사용이 어디인지부터 확인하고 넣는다.
- 평가 단계 설계 시 "라벨이 다른 변수와 confound되어 있는가"를 체크리스트 항목으로 명시해, 우연히 서브에이전트가 알아차리길 기다리지 않고 항상 확인하게 만든다.
- 백그라운드 작업 폴링 로직은 항상 디바운스를 기본값으로 넣는다.
- 데이터 누수가 확인되면 "feature를 손보면 고쳐지는가"를 먼저 싸게(진단용 보조 분류기 하나로) 확인하고, 그 결과로 국소적 수정을 계속 시도할지 새 데이터/문제 재정의가 필요하다고 결론 낼지를 빨리 판단한다 — 안 될 걸 모르고 feature 조합을 계속 바꿔가며 재학습을 반복하는 게 가장 비싼 실패 모드다.
